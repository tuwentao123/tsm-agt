# 取消机制设计规范（Cancellation Spec）

> 适用范围：tsm-agt 运行时（Runtime）、内核模型（Kernel）、Web 接入层及工具执行层。
> 目标：在保持结果一致性和资源安全回收的前提下，实现“面向当前轮次的可预期取消”。

---

## 1. 设计总原则

1. **当前轮次优先**：取消请求只针对当前活动轮次（current turn），不得越权直接操作历史轮次的资源或结果。
2. **单一入口，多级传播**：取消信号从统一入口注入（如 Runtime API / Web API），通过 Task → Turn → Step → Process / Tool 多级向下传播。
3. **显式状态机驱动**：取消不依赖隐式异常或超时，而是通过明确的状态机（如 TaskState / TurnState / ProcessState）来描述和驱动。
4. **可恢复与幂等**：取消操作必须幂等（重复取消不会导致额外副作用），并为“继续/重试”预留扩展点（如重新创建新轮次）。
5. **结果一致性优先于即时回收**：对于已经写入工作空间的结果，优先保证“一致且可解释”的最终状态，而不是盲目回滚所有改动。
6. **跨层可追踪性**：从 Web UI / API 到内核执行，再到底层进程与工具，所有取消行为需具备可追踪的日志与事件链路。

---

## 2. 抽象模型与术语

### 2.1 核心对象

- **Session**：用户会话，由多个 Task 组成。
- **Task**：用户请求在 Runtime 中的抽象表示，一个 Task 可以包含多轮交互（Turn）。
- **Turn（轮）**：一次“用户输入 → Agent 推理与执行 → 输出”的完整周期，取消语义默认绑定在 Turn 级别。
- **Step**：Turn 内部的细粒度执行单元（例如：一次模型调用、一次工具执行、一次文件写入事务）。
- **Process**：由工具执行或外部命令创建的操作系统级进程或进程组。
- **Tool Call**：抽象的外部能力调用，可能是本地命令、网络请求，或对 Runtime API 的调用。

### 2.2 状态与信号

- **Cancel Signal**：取消请求的抽象表示，携带 `scope`（如当前 Turn）、`reason`、`source`（发起方）、`timestamp` 等信息。
- **TaskState / TurnState / StepState**：
  - `PENDING`：尚未执行。
  - `RUNNING`：正在执行。
  - `CANCELLING`：收到取消信号，正在执行取消协议。
  - `CANCELLED`：取消完成，进入终态。
  - `COMPLETED`：正常完成。
  - `FAILED`：异常失败（非预期取消）。

## 3. 取消信号的传播路径

### 3.1 入口层（Web / Local API）

**入口约束：**

1. 入口只允许针对一个明确的 `Task` / `Turn` 发起取消请求，必须包含：
   - `task_id`
   - `turn_id`（如省略则默认为当前活动轮）
   - `reason`（可选）
2. 入口层应立即更新 Runtime 中对应 Turn 的逻辑状态（如标记为 `CANCELLING`），并向下游执行层发出取消信号。
3. 入口层必须具备幂等性：重复相同的取消请求返回同一逻辑结果。

**接口形态示例（仅规范，不限定具体实现）：**

- `POST /runtime/tasks/{task_id}/turns/{turn_id}/cancel`
- `local_api.cancel_turn(task_id: str, turn_id: str, reason: str | None)`

### 3.2 Runtime 与内核模型层

Runtime / Kernel 层负责将取消信号从逻辑对象映射到具体执行单元：

1. **Turn 级状态机推进：**
   - 当入口层标记 Turn 为 `CANCELLING` 时，Kernel 应：
     - 暂停创建新的 Step（如新的模型调用、新的工具调用）。
     - 将当前 RUNNING 的 Step 标记为 `CANCELLING` 并开始下游取消流程。
2. **Step 内部传播：**
   - 对每个 RUNNING 的 Step，Kernel 调用对应的执行适配器（如 Tool Adapter、Process Adapter）触发取消。
   - Step 自身需要等待下游执行结果或超时，再更新 StepState 为 `CANCELLED` / `FAILED`。
3. **多 Step 协调：**
   - 对于同一 Turn 下多个并行 Step：
     - 统一标记为 `CANCELLING`。
     - 分别调用下游取消逻辑。
     - Turn 在所有 Step 的状态达到终态后，再更新为 `CANCELLED` 或部分 `COMPLETED`。

### 3.3 底层执行与工具层

对底层执行单元（Process / Tool Call）的取消策略：

1. **进程与进程组：**
   - 如果工具以“进程组”方式启动，则取消时应对进程组发出信号：
     - 首选 `TERM`（温和终止），在合理等待后再视情况发送 `KILL`。
   - 如果只创建单一进程，则只对该进程进行上述终止操作。
   - **约束：**不得对无关的外部进程进行取消（需有明确的进程/组 ID 绑定关系）。
2. **正在运行的工具调用：**
   - 工具适配层需要提供 `cancel()` 或等价接口：
     - 对本地命令：发送进程信号。
     - 对远程服务：调用相应的取消/中断 API。
   - 工具必须返回一致的最终状态：`CANCELLED` / `FAILED` / `COMPLETED`。
3. **未启动或已完成的工具调用：**
   - `PENDING` 状态的工具调用直接标记为 `CANCELLED`，无需执行实际取消操作。
   - 已进入 `COMPLETED` / `FAILED` 的调用无需重复取消，仅记录取消请求被忽略的事实（用于审计）。

## 4. 运行检查点设计

### 4.1 检查点的语义

检查点用于：

1. **在长链路执行中周期性检查是否有新的取消信号。**
2. **划分可恢复与不可恢复的边界。**
3. **保证复杂执行流程的可中断性与结果一致性。**

典型检查点位置：

- 在每次模型调用前后。
- 在每次工具调用前后。
- 在每次持久化写入（文件/数据库）前后。
- 在长循环或批处理任务的迭代内部。

### 4.2 检查点行为规范

在进入一个检查点时，执行方应：

1. 查询当前 Turn / Task 的最新状态：
   - 若为 `CANCELLING`：
     - **在未持久化写入之前**：立即停止后续执行，返回 `CANCELLED`。
     - **在已完成关键写入之后**：
       - 继续执行必要的收尾逻辑（如刷写缓存、关闭资源），然后返回 `CANCELLED`。
   - 若为 `RUNNING`：正常继续。
2. 将检查点信息写入日志或运行时事件流，便于后续审计和重放。
3. 如果检查点处存在事务（如文件写入事务或数据库事务）：
   - 明确事务在取消时的策略：
     - **要么整体回滚**，保证逻辑上一致。
     - **要么将部分完成的事务以“已知中断点”的形式记录**，供后续继续/修复。

### 4.3 检查点与幂等

为了保证重复取消或重试不会导致混乱：

1. 检查点操作应设计为幂等：同一检查点在同一 Turn 内重复执行不会产生额外副作用。
2. 对已经标记为 `CANCELLED` 的 Turn，再次进入检查点时应直接返回终态，不再进行实际执行。

## 5. 资源回收与结果一致性处理

### 5.1 资源回收范围

取消时需要考虑的资源包括：

1. **进程与进程组**：由工具或核心逻辑启动的操作系统进程。
2. **文件句柄与网络连接**：打开的文件、Socket、HTTP 会话等。
3. **Runtime 内部对象**：如缓存对象、上下文对象、模型会话句柄等。
4. **临时工作空间文件**：例如中间结果文件、临时日志文件等。

### 5.2 回收策略

1. **进程与进程组：**
   - 按“TERM → 等待 → KILL”的顺序进行。
   - 在发送 `KILL` 前必须确认不存在关键持久化操作正在进行中，或已经有更高层的事务保护。
2. **文件与连接：**
   - 在取消流程中显式调用关闭操作，并确保此行为在日志中可见。
3. **Runtime 内部对象：**
   - 通过上下文管理器或显式 `close()` / `dispose()` 接口进行释放。
4. **临时文件：**
   - 对明确标记为临时的文件，可在取消完成后删除。
   - 对可能包含有价值中间信息的文件，应以“标记 + 日志记录”的方式保留，并在后续人工或自动流程中统一处理。

### 5.3 结果一致性

1. **逻辑一致性：**
   - 同一 Turn 的最终状态必须可解释：
     - 要么全部关键 Step `COMPLETED`，Turn 为 `COMPLETED`。
     - 要么在取消信号下，所有 Step 至少达成 `CANCELLED` / `FAILED` 的可追踪终态，Turn 为 `CANCELLED` 或部分成功的 `FAILED`。
2. **持久化一致性：**
   - 对关键持久化操作应采用事务或写前日志：
     - 在取消发生时，要么整体回滚，要么留下一致的（即使不完整）状态及对应运行日志。
3. **用户视角一致性：**
   - Web / API 层返回给用户的状态需与内部状态机一致：
     - 提供“已取消”、“部分成功但已终止”、“已失败”的明确区分。

## 6. 与现有开源方案的设计对齐

> 本节用于指导实现方向，与 Codex、Hermes 等开源 Agent 的取消机制进行抽象对齐，非逐字实现要求。

1. **任务/轮次级取消（Task/Turn-level Cancellation）：**
   - 与多数开源 Agent 一致，取消主要绑定在当前任务/轮次，而非整个 Session；
   - 通过显式状态机来区分正常结束与用户发起的取消。
2. **进程/工具级中断：**
   - 借鉴常见的执行器/适配器模式，在工具执行层提供统一的取消接口；
   - 对本地进程采用进程组信号，对远程调用采用 API 级取消或超时策略。
3. **检查点与可恢复执行：**
   - 与开源方案中的“中断点 / checkpoint”类似，在长链路推理与执行中嵌入检查点，允许安全停止与后续恢复。
4. **幂等与事件驱动：**
   - 使用事件流或日志来记录取消请求和执行结果，确保重复取消或重试不致产生矛盾状态。

## 7. 实施要求与扩展点

### 7.1 实施要求（代码级标准）

1. **接口层：**
   - 在 Web / local API 中增加显式取消接口，并将取消请求映射到 Runtime Task/Turn 对象。
2. **Runtime / Kernel 层：**
   - 为 Task / Turn / Step 增加或完善状态字段及状态机逻辑（含 `CANCELLING` / `CANCELLED`）。
   - 在内核执行主循环中插入检查点逻辑，周期性查询取消状态并执行相应分支。
3. **执行器与工具层：**
   - 为核心工具执行路径增加取消接口适配（如进程信号、远程 API 取消）。
   - 在工具执行开始与结束处增加检查点，以确保可中断和资源释放。
4. **资源管理与日志：**
   - 在进程管理、文件/连接管理等组件中增加取消态下的释放逻辑。
   - 增强日志记录，确保每一次取消请求与结果可追踪。

### 7.2 扩展点

1. **优雅降级策略：**
   - 在无法立即取消（如远程服务不支持取消）的情况下，采用超时 + 状态标记方式实现“逻辑取消”。
2. **跨 Task/Turn 的高级取消：**
   - 后续可设计 Session 级或用户级的批量取消能力，但需在实现上与当前 Turn 级取消严格区分，以避免误伤。
3. **恢复与重试：**
   - 在取消后支持“从最近检查点重新开始”，或通过新的 Turn 复用已有上下文继续执行。

---

## 8. 结语

本规范定义了 tsm-agt 中取消机制的整体架构、信号传播路径、检查点设计以及资源回收与结果一致性策略。后续代码实现应以本规范为基础，在具体模块（Web、Runtime、Kernel、工具执行器、资源管理器）中逐步落地，并在测试用例中覆盖：

- 当前轮次取消的常规场景；
- 并行工具执行下的取消与资源回收；
- 检查点处的取消行为与结果一致性；
- 重复取消与重试的幂等性。
