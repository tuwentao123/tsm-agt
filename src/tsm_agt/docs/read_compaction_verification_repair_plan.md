# 读取复用、压缩交接与验证推进的修复方案

日期：2026-11-08。状态：实施方案，已补充影响面复审与第一版范围。

目标是让模型承接已完成的工作、按需取回原文、选择并执行合适验证；Runtime 提供真实状态、权限边界、上下文管理与有界执行。复用现有 WorkingMemory、Todo、检查点和工具账本，不另外建立一套任务状态机。

## 1. 已确认的问题和边界

样本：`turn-cf412ba1f9d441c29f1f3f31e8464ea5`。

- 25 次主流程模型请求，7 次压缩额外产生 34 次摘要请求，共 59 次逻辑请求。
- 115 次实际工具调用中，90 次读取文件，4 次补丁调用修改 3 个文件；测试执行为 0。
- 15 次读取返回同一文件版本、相同正文。这不等于 15 次都把正文重复发送给模型；需结合当时的请求投影判断。
- 第一笔补丁前有 54 次工具调用，其中读取 42 次，耗时约 8 分 23 秒；期间发生了 4 次压缩。
- 现有磁盘缓存与 `read_result_reuse` 已实现部分复用；后者会检查被引用正文是否仍在请求内，这个正确约束必须保留。
- 前置 artifact-read 守卫根据任务历史与调用参数判断重复，没有对应的当前窗口可见性判断。它可能要求复用已经离开窗口的原文；提示里的“改变有效参数”又允许通过改变 `max_lines` 重取相同内容。
- 摘要器按最多约 32KB 文本分片逐个调用模型，返回滚动摘要；摘要指令要求重新读取被省略的 Skill 正文。
- 当前还存在独立的 `history_soft_tokens` 压力条件。它与完整请求预算可以分别触发压缩，需要记录具体触发原因后统一调优；不能只看到默认 80% 就认为压缩只由该比例触发。

修改后回读、新范围读取、压缩后重新取得确实缺失的原文都可以是合理行为。评价重复必须同时考虑版本、实际范围与当前窗口可见性。

## 2. 核心不变量

1. 历史上读过不等于本次模型请求仍然看得到。
2. 引用必须能在最终请求中找到对应正文；否则补回原文或明确说明不可用。
3. 文件与授权状态重新检查后才能复用；缓存不授予额外路径权限。
4. 原始工具结果和账本保持真实，缩减正文发生在模型投影层，不改写历史事实。
5. 摘要不能成为授权、验证成功或任务完成的证据。
6. 当前 Skill 以已加载的真实版本和原有权限层级保留，不能由摘要重新生成其指令。
7. 模型选择验证方法与执行时机；Runtime 记录执行事实，不替模型自动运行测试。
8. 取消、预算耗尽、摘要失败均有可见的可恢复结果，旧后台任务不能覆盖新轮检查点。

## 3. 读取复用：统一历史观测与当前窗口可见性

复用现有文件缓存、读取观测记录和请求投影，统一身份与查询接口。历史索引定位内容，当前窗口索引决定能否只给引用；两者不能互相代替。

观测身份至少包含：任务与授权根、规范路径、完整文件内容哈希、实际返回的行列范围、正文哈希、来源调用/事件/制品引用。单纯的 `max_lines` 或原始参数字符串不作为正文身份。

| 状态 | 处理 |
| --- | --- |
| 同版本、同范围，正文仍在最终请求中 | 成功返回短引用；不再次放入相同正文 |
| 同版本、同范围，正文已离开窗口 | 校验权限及当前版本后，从缓存/制品补回必要原文；不能返回空引用 |
| 同版本，但目标范围未读 | 取得所需范围；已经读过的其他范围不构成阻止理由 |
| 文件变更 | 使旧版本的当前内容复用记录失效，读取新版本 |
| 权限撤销、路径变更、文件删除或无法验证缓存版本 | 执行正常访问检查，按真实结果返回；不伪造 unchanged |

优先替换 `ARTIFACT_ALREADY_READ` 的普通重复读取报错路径：能够提供已有内容时提供成功观测，缺正文时允许恢复原文。重复本身用于观测和低进展提示，不制造一轮无效的错误纠正。

短引用只在最终模型请求投影中生成。工具执行时的窗口还可能被下一步压缩，不能在前置守卫中根据暂时可见性写入不可恢复的裸引用。第一版保持完整原始结果或可校验、可补回正文的制品；原有 `project_read_results` 继续在装配后选择真实来源。该函数已经能合并不同 `max_lines` 返回的相同实际窗口，不能把已有能力算成新方案的收益。

`max_lines=50/80/100` 最后都返回同一份 32 行文件时，应归一成同一实际窗口。局部重叠先保证目标内容完整正确，再在请求投影中合并覆盖区间；不要先引入容易丢行列的多段返回协议。

每次访问仍检查授权根、规范路径和文件版本；外部编辑、原子替换、同长度改写、符号链接变化、长行列偏移、缓存淘汰必须覆盖。

改写读取提示：`next_cursor` 表示还有未返回内容，只有当前问题需要时继续读取，不再暗示必须把整个文件读完。优先搜索/定位，再读取相关函数或范围。

## 4. 交接：把事实与工作进度保存在现有状态里

在 WorkingMemory/Todo 与执行上下文投影上扩展一个有界交接视图：

```text
当前请求及其来源：继续哪项工作，最新约束是什么
模型声明的阶段：调查 / 实现 / 验证 / 汇报 / 阻塞
已定位信息：文件版本、相关范围、结论和来源
已完成修改：路径、修改版本/内容指纹、工具事件引用
活跃 Skill：注册身份、资源路径、版本、原文或可恢复制品引用
验证计划：方法、覆盖目标、已确认入口、预期可观测结果
验证记录：是否实际发起、对应修改版本、结果/输出引用、覆盖缺口
下一步与阻塞：具体缺少什么，或已准备执行哪一项动作
```

确定性事实从账本投影：成功修改、实际执行、退出码、工具错误等不依赖模型重新口述。阶段、推理结论与计划仍由模型维护，注明它们是模型声明，不把声明当成运行事实。

阶段不是新的 TaskState，也不是固定顺序的执行门禁。测试发现新问题后可以回到实现；用户改变任务、要求不运行测试或只做分析时，按最新约束处理。

只在实际阶段/计划变化时更新作者状态，不为每次读取增加 Todo 写入或额外模型调用。

第一版优先提供现有状态与事件的只读交接视图，复用 plan、completed_work、remaining_work 和 evidence，避免一次引入多套需要同步的阶段字段。派生索引有明确重建来源，不成为新的事实存储。确需新增持久字段时，再单独版本化与迁移。

当前轮与上一阶段的真实请求要优先于长期 Task.goal，避免“继续啊”恢复成最早一轮已经过时的任务解释。

### 活跃 Skill 的保留

- 保护当前工作仍需要且已成功加载的 Skill 主文与已使用资源，设置总容量与明确退出范围。
- 同版本且正文已重投影的新窗口，无须仅因发生压缩再调用 `skill.load`。
- Skill 内容变更、任务切换、权限变化或正文未保留时，再按实际情况更新/读取。
- 保持原本的消息角色、来源和指令权限；外部文本不升级为系统指令。此机制不执行 Skill handler、安装依赖或授予审批。
- 关键命令、修改版本与真实验证结果从结构化状态重建，不能只靠一份短自然语言摘要承载。
- Skill 以 Task/当前请求和资源版本限定活跃范围；用户转入分析或切换目标时重新确定适用性。容量不足时整份移出可选资源并明确可再取回，不静默截断安全限制后仍声称指令完整。

## 5. 压缩：先清理与交接，再做必要的语义摘要

候选窗口生成顺序：

```text
原始检查点和历史
→ 投影去重、移出可通过制品定位的大正文
→ 生成当前事实、工作进度和活跃 Skill 的交接视图
→ 按完整请求预算选择可压缩的旧历史
→ 对需要语义保留的增量历史生成摘要
→ 重新装配最终请求，校验引用、工具协议和输入预算
→ 原子提交新窗口与检查点
```

具体要求：

1. 按最终请求的消息、工具定义、图像预留和输出空间估算，结合 provider 实际 usage 校准；估算不是精确计费值。
2. 标注 `context_capacity`、`history_pressure`、`latency_target`、配置变化等触发原因，解释每一次压缩。历史软预算应作为明确的内容分配策略，避免在容量充足时重复触发昂贵摘要。
3. 触发线与压缩目标之间留出可用空间，防止刚压缩后一次读取又再次触发；具体比例根据项目回放校准。
4. 摘要输入先去重，优先处理上次摘要之后尚未覆盖的历史；已有事实与正文引用不反复送去总结。
5. 按摘要请求的实际可用 token 预算分片，替换固定 32KB 分片。普通情况以一次摘要请求为优化目标；较大输入允许有界分片，次数、token 与时限均显式配置和记录。
6. 摘要保留决定和理由、未解决问题；完整代码、已读范围、权限、测试结果由原文/事实视图承担。
7. 摘要失败、超时或取消时不提交候选窗口。同一源摘要失败不能无新信息地无限重试；采用显式降级，无法安全容纳请求则记录可恢复停止。
8. 提交前核对源检查点版本与当前轮，拒绝旧摘要覆盖新的用户输入；工具调用与结果必须成组保留，审批绑定与未知执行结果保持原样。

增量摘要需记录覆盖的源事件范围、源哈希和摘要版本。新事实可能否定旧结论，不能机械把旧摘要与增量拼接。发现游标缺口、用户目标变化或不兼容配置变化时重新评估交接，按预算选择重建或保留明确的冲突。提交完成前原历史仍是可恢复来源。

稳定系统提示词与工具定义保持稳定。当前读取索引、预算提示与工作事实在受控上下文段/追加事件中呈现，避免每次读取都重写长提示词前缀；窗口根快照只在真实窗口/配置边界重建。

## 6. 验证推进：让模型承接已知入口并实际执行

调整 `verify-change` 与协调提示的重点：

- 已有有效验证入口、当前实现已准备验证时，使用该入口执行并读取结果。
- 只有存在具体信息缺口时再发现入口，不在每次继续或压缩后重复完整项目调查。
- 加载 Skill、读取测试源码、写入文件、看到无关命令退出 0 均不等于验证成功。
- 测试报错后依据输出定位所需代码，修复后选择受影响检查；由模型决定实际方法与覆盖范围。

支持命令、浏览器交互、静态检查或明确的人工检查，不把 pytest 等单一框架硬编码成通用验证方法。命令计划可记录 argv、cwd、验证目标与预期观测，仍走现有执行和授权通道。

Runtime 提供简洁的真实状态，例如“这些文件已修改，尚无对应版本的检查执行记录”。只在相关状态变化时追加，不在每次工具调用后重复催促。

验证记录区分：未发起、未启动、执行中、执行失败、通过、覆盖不足、用户要求跳过、因后续相关修改已过期。一次旧版本通过不能证明当前代码通过；源码读取不能产生通过记录。

执行事实与覆盖判断分开：命令退出 0 是执行事实，“相关功能通过”是需要覆盖范围和证据支持的模型判断。验证记录还需包含对应修改、所选检查与输出引用，不能把任意成功命令归为验证成功。发现代码已改不代表实现已经完成，不据此强制模型立刻进入测试。

连续重新读取或重载 Skill 但没有新增信息时，向模型提供已知信息与下一步缺口，要求选择推进动作或说明阻塞。沿用、修正既有重复读取/探索策略，避免叠加更多返回错误的业务门禁。

不自动运行测试，不替模型指定命令，不新增“没加载指定 Skill/没跑固定测试就不能结束”的硬规则。验证推进是否改善，必须用真实模型行为回放验收。

## 7. 预算与页面观测

分别记录主请求、摘要请求、验证辅助请求及其物理尝试；逻辑请求与重试次数不能混为一谈。每次都关联到父 Task/Turn。

- 工具提议数、前置拒绝数、实际调度数、文件缓存命中/真实 I/O、重复正文投影节省量分别统计；命中缓存不抹去已经发生的调用。
- 全部模型请求纳入累计 token/耗时统计，摘要有独立子预算；有可靠价格与缓存计费明细时才显示费用估算。
- 分开呈现上下文容量、单轮累计消耗、单步并发与请求重试预算，避免一个数字表达多种含义。
- 临近限额时提前提示模型与用户，预留收尾/记录检查点的空间。已有 90/120 默认值在基线回放后校准，不作为行业标准。
- 触顶后复用已修复的未完成边界：记录具体原因、已用/剩余/拟发起量、保留进度并结束等待；不执行超额批次，不重放结果未知操作。
- 页面显示“正在压缩/摘要请求数”“准备验证/实际验证结果”“已停止及原因”，与事件和检查点一致。

预算配置保留旧计数语义，新增总请求/物理尝试/摘要子预算先观测后明确启用，不能把原本 90 次主请求静默改为所有请求共用 90 次。

续做契约需要单独明确：原轮恢复不会天然获得新预算；新消息开启新轮沿用新轮预算。原轮如需补额，应通过明确、有界、可审计的策略授权，并从未执行的边界继续，不能自动重放已提交或结果未知的操作。额度仍不足时先报告，而不是重复消耗一次模型请求后再次触顶。

## 8. 代码落点与实施顺序

| 顺序 | 修改范围 | 目的 |
| --- | --- | --- |
| 1 | provider 调用观测、`context.py`、`sdk/ui_events.py` 与评估脚本 | 建立分类统计和压缩触发原因；先取得可比较的基线 |
| 2 | `rule_based_artifact_read/policy.py`、`turn_tool_batch.py`、`core_tools.py`、`read_result_reuse.py`、文件缓存 | 统一版本/范围/可见性；修复普通重复读取报错和分页提示 |
| 3 | WorkingMemory/Todo、执行上下文投影、`context_window.py`、Skill 加载资源投影 | 持久交接、保留活跃指令，减少重新调查 |
| 4 | `context.py`、`model_context_summary.py`、`compaction.py`、`ContextSummaryPort` | 增量、按 token 分片、有界摘要与事务化窗口切换 |
| 5 | `verify-change`、协调提示、执行事实投影 | 模型选择并执行对应验证，记录真实覆盖与版本 |
| 6 | 总预算配置、页面、真实模型评估与灰度开关 | 统一止损、透明展示并校准阈值 |

遵守现有依赖边界：Core 依赖 Port，具体能力在 composition 注入；Web 不导入具体 adapter。现有技能加载的两项跨层依赖检查失败应单独修正并记录，不与本方案的效果混淆。

## 9. 验收与回退

确定性测试：

- 不同 `max_lines` 返回同一小文件；同版本新范围；跨窗口恢复；长行列偏移；外部修改、路径权限变化、缓存淘汰。
- 最终请求中相同观测正文只保留一份，所有引用可解析；原文不在窗口时补回内容。
- 压缩失败不提交、取消后旧摘要不覆盖新轮、工具调用与结果不被拆开、活跃 Skill 同版本正文有效保留。
- 验证事实来自真实执行与输出；用户禁止执行得到遵守；相关文件再修改后旧结果正确标识其版本。
- 所有请求类型和失败尝试计入正确预算；触顶、拒绝、取消均结束对应等待。

行为回放：

1. 使用本轮原始事件固定事实基线，再在隔离项目快照中运行真实模型；历史工具结果回放不能替代真实行动选择评估。
2. 覆盖“继续已有实现”“小范围修复”“修改后验证失败”“压缩期间新消息”“有工具审批”以及无需测试的分析请求。
3. 对同一模型和配置比较：首笔有效修改延迟、当前窗口仍有原文却重读的比例、重复 Skill 加载、摘要调用及 token、实际验证与覆盖、总耗时。
4. 将“压缩后必要补回”和“当前窗口内可避免重复”分开；15 次同正文重复只能作为待分类的历史样本，不能直接全记为可避免。
5. 以功能与权限边界保持正确、无假验证/假完成、开销较基线降低作为联合验收，不用一个漂亮的调用次数代替工作结果。

按步骤独立提交和灰度，保留原始账本及检查点兼容读取。新优化关闭后回到已有完整正文路径，不回退成悬空引用或已删除的上下文。长期目标由多任务、多模型回放评估，不承诺只改一句提示词就能让模型百分之百选择正确行动。

## 10. 影响面复审与第一版收敛

### 10.1 必须处理的风险

| 优先级 | 风险 | 处理要求 |
| --- | --- | --- |

### 10.2 可以解决到什么程度

- 已确认的守卫参数绕行与窗口可见性冲突：有确定性修复路径，可直接构造输入验证。
- 重复正文与压缩后悬空引用：可通过最终请求契约测试验收；现有投影已有部分正确能力，应扩展和保留。
- 压缩后被迫重新加载同版本活跃 Skill：有效正文成功重投影后不再具有协议上的重新加载要求；模型是否仍主动加载需实测。
- 34 次摘要请求的开销：有明确减少方向，降幅取决于真实输入、分配策略及摘要质量；不能预先承诺恒定一次。
- 首次修改前长探索：交接与定点读取应能减少重建成本；模型本身的探索选择仍需行为评估。
- 修改后未执行测试：状态与提示改善其条件，不能由此保证自主模型每次选择正确命令。对应代码修改样本必须实际执行相关验证才算行为验收通过。
- 本次预算异常造成页面假执行：已有独立修复与测试；还需维持所有后台退出路径均有持久完成/挂起/未完成/中断/失败边界的生命周期约束。

### 10.3 第一版范围

先交付观测、守卫与最终投影的一致性、读取提示，以及已有状态的只读交接和有界活跃 Skill 保留。其次修改摘要策略；最后启用新的预算策略。区间合并、多套状态字段、大范围检查点迁移不与第一版捆绑。

每一步分别回归读取正确性、权限、并行批次、压缩与重启、审批和上下文取消；影子观测确认匹配关系后，再切换行为。最后在相同项目快照与模型配置下做真实行为对照，检查“少调用”和“完成实现并验证”同时成立。

本次复审的基线验证：相关现有测试 41 项通过，覆盖读取投影、窗口管理、读取策略及工具预算边界。这是现有行为的回归结果，不是尚未实施的新方案已经通过验收。

另有两个无外部模型请求的最小复现：同一 32 行文件以原参数重读要求复用，改 `max_lines` 为 80 后却允许；工具预算为 1、提议批次为 2 时，首次与原轮恢复都停在相同预算边界。这两项作为实施时的明确回归样本。
