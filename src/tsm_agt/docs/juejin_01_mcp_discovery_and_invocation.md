# 接入了 200 个 MCP 工具，模型每次都需要看它们的说明吗？

> 本文要解决的问题：Agent 接入的工具越来越多，每次发给模型的工具说明也越来越长。用户只想查一个报表，模型却收到了报表、知识库、工单等一大批用不上的工具说明。
>
> 我们把它改成：先告诉模型有哪些能力，需要某项能力时，再查询具体工具怎么用。本文用一次“查报表”的过程，讲清楚这个改造。

## 一、先把三个角色说清楚

假设用户向 Agent 提出一个请求：

“帮我查一下演示报表的数据。”

完成这件事，需要三个角色配合：

| 角色 | 在这个例子里负责什么 |
| --- | --- |
| 模型 | 理解用户的问题，决定查什么、用哪个工具，并根据结果回答 |
| Agent 程序 | 把工具信息发给模型，检查模型提出的调用，再实际执行 |
| 报表 MCP 服务 | 一个提供报表功能的程序，接收查询参数并返回数据 |

这里说的“MCP 服务”，可以是本地启动的程序，也可以是通过 HTTP 连接的远程程序。

一个服务可以提供多个工具。例如，报表服务可以同时提供“列出报表”“查询报表数据”“导出报表”三个工具。

模型不会凭空知道这些工具怎么用。Agent 需要告诉它：工具叫什么、能做什么、需要哪些参数。这些信息就是本文所说的**工具说明**。

## 二、原来的问题：只查一个报表，却带上了所有说明

假设 Agent 接入了 20 个 MCP 服务，每个服务提供 10 个工具，总共就是 200 个工具。

原来的做法是，把这些工具的说明都放进模型请求里：

```text
用户：查一下演示报表的数据

模型收到：
  用户的问题
  报表工具的说明
  知识库工具的说明
  工单工具的说明
  ……共 200 个工具的说明
```

这样做的好处是，模型可以直接从列表中选择工具。

但随着工具增多，问题也越来越明显：

- 很多工具与当前问题无关，却仍然占用输入。
- 一个复杂工具的参数说明可能很长，200 份说明会明显增大请求。
- 工具列表发生变化时，发给模型的内容也可能跟着变化。

还有一个容易遇到的情况：某个 MCP 服务连接得比较慢，第一条模型请求发出时，它还没有准备好。后来 Agent 程序已经拿到了它的工具，模型使用的列表却可能还是之前那份。

因此，我们需要同时回答两个问题：**怎样少发无关说明？模型又怎样查到自己需要的工具？**

## 三、改成什么样：先看能力目录，需要时再查用法

改造后，模型先看到的是一份简短目录：

```text
可以使用的 MCP 服务：
  reports：查询报表
  knowledge：查询知识库
  tickets：查询工单

两个可调用的工具：
  core.mcp_discover：查找工具，了解它怎么用
  core.mcp_call：调用选中的工具
```

这里的“固定入口”，说的就是这两个工具。无论后台接入了多少 MCP 工具，模型都可以通过它们查询和调用。

模型第一次不需要看到 200 份完整说明。遇到报表问题时，再查报表工具；遇到工单问题时，再查工单工具。

| 问题 | 改造前 | 改造后 |
| --- | --- | --- |
| 模型一开始看到什么 | 全部 MCP 工具的详细说明 | 简短服务目录，以及查询、调用两个入口 |
| 什么时候了解具体参数 | 每次请求都携带所有参数说明 | 需要某个工具时再查询 |
| Agent 程序是否仍保留全部工具 | 保留 | 仍然保留 |
| 模型是否可以直接完成业务查询 | 可以，但要选择具体工具 | 可以，通过调用入口执行选中的工具 |

文件读取、运行命令等基础工具仍按原有方式提供。这里调整的是 MCP 工具进入模型请求的方式。

## 四、用一次“查报表”走完整个流程

### 第一步：用户提出问题

用户说：

“帮我查一下演示报表的数据。”

模型看到能力目录中有一个 `reports` 服务，说明它能查询报表。

### 第二步：模型查找合适的工具

模型调用 `core.mcp_discover`，查询报表服务里与“报表”有关的工具。

Agent 返回类似的信息：

```text
找到工具：mcp.reports.query_dashboard
用途：按报表编号查询数据
需要的参数：dashboard_id，类型为字符串
调用方式：通过 core.mcp_call 提交工具名称和参数
```

实际结果会包含机器可读的参数定义，供模型按要求组织调用。这里先用文字表示，方便理解。

### 第三步：模型提交查询

模型现在知道了两件事：

- 应该调用 `mcp.reports.query_dashboard`。
- 需要提供报表编号 `dashboard_id`。

于是，它通过 `core.mcp_call` 提交：

```text
要用的工具：mcp.reports.query_dashboard
查询参数：dashboard_id = dashboard-demo
```

### 第四步：Agent 检查这次调用

Agent 程序不会直接相信模型提交的内容，而是先检查：

1. 这个工具当前是否存在。
2. 参数是否完整，类型是否正确。
3. 这次操作是否允许，是否需要用户授权。

例如，报表编号要求是字符串，模型却传了一个数组，就会先收到参数错误，实际查询不会发出去。

### 第五步：报表服务执行查询

检查通过后，Agent 才把参数交给报表 MCP 服务。

报表服务执行查询，返回数据。

### 第六步：模型根据结果回答

Agent 把查询结果发回模型，模型再组织成用户能读懂的回答。

完整过程可以连起来看：

```text
用户提出报表问题
  → 模型看到“报表服务”这条能力线索
  → 查询有哪些报表工具、需要哪些参数
  → 提交选中的工具和参数
  → Agent 检查并执行
  → 报表服务返回数据
  → 模型回答用户
```

在这个过程中，知识库、工单等无关工具的详细说明都不必提前发送。

## 五、少发给模型，为什么不会把工具弄丢

因为有两份用途不同的列表：

| 列表 | 谁使用 | 保存什么 |
| --- | --- | --- |
| 后台完整工具目录 | Agent 程序 | 已发现工具的名称、说明、参数要求等 |
| 发给模型的能力目录 | 模型 | 简短服务介绍，以及查询入口 |

后台保留完整目录，模型按需要查询其中的内容。

所以，“不把 200 份说明都发给模型”，并不等于“后台只剩两个业务工具”。两个入口后面，仍然可以找到已注册的具体工具。

当前代码会在存在 `core.mcp_call` 时，从模型请求的工具列表中移除逐项暴露的 `mcp.*` 工具。后台注册的工具不会因此被删除。

这部分代码在 [conversation_loop/loop.py](https://github.com/tuwentao123/tsm-agt/blob/main/src/tsm_agt/core/conversation_loop/loop.py)。

## 六、发现过的工具和查询结果，后面还能看到吗

可以。查询工具返回的说明，以及业务工具返回的数据，都会进入对话历史。

例如，模型刚查到 `query_dashboard` 的参数要求，接下来就可以根据这份说明发起调用，不需要再把所有工具定义加入请求。

如果后续还要调用同一个工具，而参数说明仍保留在上下文中，模型可以继续参考。没有必要规定每次业务调用前都必须重新查目录。

不过，这些内容也会占用后续输入。它们可能在长会话压缩时被移出，参数定义也可能发生变化。缺少当前用法时，模型需要重新查询。

因此，这次改造减少的是**提前发送的无关说明**，不是让工具说明和结果从此不占上下文。

## 七、谁负责连接 MCP？查询时又是谁在等待？

**连接、启动和等待都由 Agent 程序执行。模型只负责提出工具调用，并在拿到结果后继续分析。**

### 1. 连接一般在 Agent 启动时就开始了

Agent 读取已启用的 MCP 配置后，会开始连接和初始化：

| 配置方式 | Agent 做什么 |
| --- | --- |
| 本地命令，例如 stdio 服务 | 启动配置中的程序，再完成 MCP 初始化和工具发现 |
| 远程 HTTP 服务 | 连接配置中的地址，再完成 MCP 初始化和工具发现；不会替用户启动远程服务器 |

默认情况下，这些工作在后台进行，不会要求所有 MCP 都准备好，才允许用户开始对话。

初始化成功后，Agent 保存已发现的工具目录。后面的 `core.mcp_discover` 主要查询这份目录，不会每查一次就重新启动或连接一遍服务。

### 2. 服务还没准备好时，不一定等到成功

发现工具有一个可选参数 `wait_seconds`：

- 不传：立即返回当前状态和已经发现的内容。
- 传入大于零的值：Agent 最多等待指定秒数，上限为 5 秒，只等待已经在进行的初始化任务。
- 时间到了还没准备好：返回“仍在连接”等当前状态，初始化可以继续在后台进行。
- 初始化已经失败：返回失败状态，这个查询本身不会自动重启或重连。

因此，它不是“等到 MCP 一定启动成功再返回”。例如，远程 HTTP 服务没有运行，Agent 不能通过多等几秒把它启动起来。

### 3. 模型所谓的“等”，实际是工具调用之间的停顿

假设模型发出了下面的调用：

```json
{
  "server_id": "reports",
  "wait_seconds": 3
}
```

执行过程是：

```text
第一次模型请求结束，模型提出调用 core.mcp_discover
  → Agent 接收调用
  → Agent 发现 reports 正在初始化，最多等待 3 秒
  → Agent 得到目录，或发现时间已到，生成工具结果
  → 把结果放进下一次模型请求
  → 模型根据“已就绪 / 仍在连接 / 已失败”决定下一步
```

这几秒是 Agent 程序在等待初始化任务，不是模型一直运行着、盯着 MCP 的状态。模型选择 `wait_seconds` 参数，实际计时和等待由工具实现完成。

### 4. 还有一种等待发生在应用启动阶段

如果某个 MCP 配置为 `required: true`，Agent 启动时就会等待它完成初始化和工具发现；失败则让应用启动失败。

这个阶段使用单独的启动预算，当前默认是 30 秒。它与发现工具最多等待 5 秒，是两个不同的限制，也都不是模型自己在等待。

后台目录也不一定随时等于服务器最新目录。当前实现不能据此宣称已经支持所有远程工具变更通知。

启动逻辑见 [mcp_tool_provider.py](https://github.com/tuwentao123/tsm-agt/blob/main/src/tsm_agt/adapters/mcp_tool_provider.py)，查询与等待逻辑见 [mcp_discovery.py](https://github.com/tuwentao123/tsm-agt/blob/main/src/tsm_agt/adapters/mcp_discovery.py)。

## 八、增加一个统一入口，授权会不会变得不准确

授权仍然针对真正执行的工具。

例如，模型虽然提交的是 `core.mcp_call`，但里面指定了：

```text
实际工具：mcp.reports.query_dashboard
实际参数：dashboard_id = dashboard-demo
```

Agent 会先解析出这些内容，再检查实际工具的参数和权限。如果需要用户批准，批准的也是这项具体操作。

记录中会保留两个事实：

- 模型提出了哪次入口调用。
- 最终执行了哪个工具、使用了哪些参数。

两者用同一个 `call_id` 关联。这样既能还原模型当时提出的动作，也能知道后台实际执行了什么。

授权等待、进程重启后的恢复，以及已经完成或结果未知的操作，继续使用原有执行记录处理。增加入口不会让一次不确定的操作变成可以随意重试。

核心执行接入见 [kernel_tool.py](https://github.com/tuwentao123/tsm-agt/blob/main/src/tsm_agt/core/kernel_tool.py)。

## 九、到底少发了多少内容

我们使用同一批合成工具做了离线对照：一边把详细定义全部放进初始请求，另一边只放简短目录和固定入口。

| MCP 工具数 | 全量发送说明：估算输入 tokens | 按需查询：估算输入 tokens | 估算减少 |
| --- | ---: | ---: | ---: |
| 3 | 7,213 | 7,066 | 2.04% |
| 50 | 12,399 | 7,176 | 42.12% |
| 200 | 29,012 | 7,589 | 73.84% |

这组结果说明，工具很少时，新增入口本身也有成本，收益并不大。工具说明占输入的比例越高，按需查询的收益越明显。

但 **73.84% 不是账单减少比例**。这组数据只比较初始请求，使用的是项目预算器估算，没有调用真实模型；后续查目录、调用工具和保存结果也有成本。

例如，模型原来可以直接调用工具，现在可能先多进行一次查询。这次查询虽然通常只读本地目录，但仍会增加模型交互。

所以，后续还需要把总输入、模型调用次数、实际延迟和任务完成情况一起比较，才能判断整个任务是否更省。

复现脚本见 [evaluate_mcp_discovery_context.py](https://github.com/tuwentao123/tsm-agt/blob/main/scripts/evaluate_mcp_discovery_context.py)：

```bash
uv run python scripts/evaluate_mcp_discovery_context.py
```

## 十、怎样确认改完之后仍然能用

测试除了检查“发给模型的列表变小”，还验证了这些实际场景：

| 场景 | 应该发生什么 |
| --- | --- |
| 服务晚一点连接成功 | 同一轮仍能查询到它的工具，并通过入口调用 |
| 模型把参数写错 | 返回明确错误，业务操作不执行 |
| 模型把入口指向普通命令工具 | 拒绝借 MCP 入口执行其他类别的工具 |
| 操作需要授权 | 展示真正的目标工具和参数，等待批准 |
| 批准前进程重启 | 恢复后仍能执行原调用并收到正确结果 |

其中，真实本地 MCP 测试覆盖了：发现算术工具、提交加法调用、等待授权、重启后批准，以及返回结果 `7`。

测试见 [test_mcp_discovery.py](https://github.com/tuwentao123/tsm-agt/blob/main/tests/test_mcp_discovery.py)和 [test_mcp_sdk_integration.py](https://github.com/tuwentao123/tsm-agt/blob/main/tests/test_mcp_sdk_integration.py)。

## 十一、需要看代码时，再展开这几个细节

前面的流程已经说明了日常使用方式。下面几个细节，主要用于理解实现。

### 1. 查询和调用的实际参数

调用 `core.mcp_discover` 的示例：

```json
{
  "server_id": "reports",
  "query": "报表",
  "limit": 5
}
```

查询结果会给出具体工具名称和参数定义。参数定义在代码中通常称为 JSON Schema，可以把它理解为“机器可读的参数要求”。

接着调用 `core.mcp_call`：

```json
{
  "tool_name": "mcp.reports.query_dashboard",
  "arguments_json": "{\"dashboard_id\":\"dashboard-demo\"}"
}
```

`tool_name` 表示要用哪个工具。`arguments_json` 是把查询参数写成 JSON 文本。

使用文本，是为了让这个入口保持同一套参数结构，而不必为每个 MCP 工具再扩展一套入口定义。Agent 收到后会解析成参数对象，再交给真正的工具。

调用还可以提供发现结果中的 `schema_hash`。它用来检查工具名称和参数要求是否与发现时一致；不一致就返回 `MCP_SCHEMA_CHANGED`，让模型重新查询。

这个值是可选的，也不能代表远程工具所有业务行为都没有变化。

固定调用入口实现在本地新增文件 `src/tsm_agt/core/mcp_call.py` 中。文件尚未提交，暂不提供 GitHub 源码链接。

### 2. 分页解决的是一次返回太多

初始能力目录最多展示 20 个 MCP 服务概述，每条用途说明最多保留 256 个字符。模型可以继续通过发现入口查询未展示的内容。

发现入口支持按服务、名称或说明中的文字筛选，也支持用 `offset` 和 `limit` 分页。查询采用子串匹配，没有额外引入向量检索。

因此，查询词和工具描述是否清楚，会影响模型能否找到合适工具；这个改造没有保证模型每次都能选对。

### 3. 两个入口是 Agent 自己的工具名称

`core.mcp_discover` 和 `core.mcp_call` 是本项目提供给模型的入口。

它们后面仍然使用 MCP 的工具发现、调用机制，没有更换远程 MCP 服务的协议。协议本身可参考 [MCP 工具规范](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2025-03-26/server/tools.mdx)。
