## 1. 三种入口 → 统一入口

### 1.1 入口表

| 入口 | 位置 | 做的事 |
|---|---|---|
| CLI | `cli.py:1509`、`cli.py:1929`（`route_runtime_input`），`cli.py:1755`（`run_agent_turn`） | 终端读一行 → 直接调 Kernel |
| Web | `web/app.py:3027` `POST /session-input`、`:3221` `POST /tasks/{id}/input`、`:3121` `POST /tasks/{id}/stop`、`:3145` `POST /tasks/{id}/cancel` | HTTP → 调 SDK；`/stream/{task_id}`（`:3527`）推 SSE |
| SDK | `sdk/runtime.py:489` `RuntimeClient.submit_user_input` | **统一入口**：三个客户端共用 |

**设计要点**：客户端只说"哪条会话 + 可选显式意图"，**路由决策归 Core**（`sdk/runtime.py:496-500`）。

### 1.2 统一入口的签名与数据格式

`sdk/runtime.py:489`

```python
async def submit_user_input(
    self, session_id: str, text: str, *, input_id: str,
    explicit_intent: RuntimeInputIntent | None = None,
    target_task_id: str | None = None,
    images: tuple[ImageBlock, ...] = (),
    workspace: Path | None = None,
) -> RuntimeCommandResult
```

| 参数 | 含义 |
|---|---|
| `session_id` | 会话 id（多轮上下文的归属） |
| `text` | 用户原文（会 `strip()`；空则报错，`INTERRUPT` 例外） |
| `input_id` | **调用方给的稳定消息 id**，用于幂等去重（同 id 同内容重放） |
| `explicit_intent` | 显式意图，见 `RuntimeInputIntent`；显式意图**永远优先**，不走判断器 |
| `target_task_id` | 显式指定操作哪个任务（默认用会话的 active task） |
| `images` | 已校验的 `ImageBlock` 元组（附件只走新建任务，不能 steer） |
| `workspace` | 多工作区时点名工作区 |

返回 `RuntimeCommandResult`（`sdk/runtime.py:131`）：

```jsonc
{ "command_id": "<input_id>", "replayed": false, "result": { /* 见下 */ } }
```

`RuntimeInputIntent`（`core/runtime_input.py:235`）：

```
STEER | REPLACE | REVIEW_PENDING_ACTION | STATUS_QUERY
NEW_TASK_AFTER_CURRENT | NEW_TASK | INTERRUPT | AMBIGUOUS
```

## 2. 会话级路由（Session-level routing）

`sdk/runtime.py:517` `_route_user_input`，按**固定优先级**走 6 个分支：

| # | 条件 | 行为 | `result.kind` |
|---|---|---|---|
| 0 | active task 处于**瞬时态**（`_TRANSITIONAL_TASK_STATES`） | 直接返回"处理中"，不新建也不 steer | `busy`（reason `task_processing_retry`） |
| 1 | 有 `explicit_intent` | 走 `_apply_explicit_intent` | `interrupted` / 新建 / `steered` / `replaced` |
| 2 | 带 `images` | **总是新建任务**（steering 只支持文本） | 会话路由结果 |
| 3 | active task 在 `AWAITING_APPROVAL` / `AWAITING_USER` | 返回提示，绝不把普通文本当成新话题 | `clarify`（reason `task_awaits_user_action`） |
| 4 | active task 在 `_RUNNING_TASK_STATES` | 调**关系判断器**决定关系 | `steered` / `replaced` / 新建 |
| 5 | 没有运行中的任务 | 走既有会话路由 | 建任务 / 直接回答 / 追问 |

三个集合的确切成员（`sdk/runtime.py:475`）：

```python
_RUNNING_TASK_STATES      = {EXECUTING, RUNNING_WORKFLOW}
_TRANSITIONAL_TASK_STATES = {CREATED, INTAKE, RESOLVING_PROJECT, SELECTING_EXTENSIONS,
                             ROUTING, PLANNING, VERIFYING, FINALIZING, INTERRUPTING, RESUMING}
_INTERRUPTIBLE_TASK_STATES= {EXECUTING, RUNNING_WORKFLOW, AWAITING_APPROVAL, AWAITING_USER}
_RELATION_CONFIDENCE_FLOOR = 0.85
```

### 2.1 关系判断器（relation judge）

`sdk/runtime.py:609` `_judge_relation`：

1. 从 registry 取 `SessionInputRelationPort`（没有则默认 `SUPPLEMENT`，reason `no_relation_judge_registered_supplement`）。
2. 组织 `context`（**输入格式**，`sdk/runtime.py:627`）：

```jsonc
{
  "session_id": "<id>",
  "recent_messages": [ {"role": "user", "text": "...", "task_id": "..."} ],  // 最近 12 条
  "active_task": { "task_id": "...", "state": "EXECUTING", "goal": "..." }
}
```

3. 调 `judge_input_relation(text, context)` → `SessionInputRelationJudgement`：

```python
SessionInputRelationJudgement(relation, confidence, reason_code)
```

`SessionInputRelation`（`ports/session_input_relation.py`）：
`SUPPLEMENT`（补充）/ `REPLACE`（替换方向）/ `UNRELATED`（无关）/ `STATUS_QUERY`（问状态）/ `ANSWER`（答复）/ `UNKNOWN`。

4. 映射与兜底（`sdk/runtime.py:568-588`）：
   - 非 `SUPPLEMENT` 且 `confidence < _RELATION_CONFIDENCE_FLOOR(0.85)` → 降级为 `SUPPLEMENT`（reason `below_confidence_floor_supplement`）；
   - `SUPPLEMENT` → `STEER`；`REPLACE` → `REPLACE`；`UNRELATED` → **先停旧任务**再新建；
   - 判断器异常 → 回落 `SUPPLEMENT`（reason `relation_judge_failed_supplement`），**绝不因为判断器坏掉而改变任务**。

### 2.2 steer / replace 的实际落地

`sdk/runtime.py:641` `_steer_active` **不自己写状态**，而是回到 Kernel：

```python
await kernel.dispatch_input_event(
    RuntimeTextInput(active.task_id, text, input_id, explicit_intent)
)
```

返回结构（`_steer_active` 组装的 `result`）：

```jsonc
{
  "kind": "steered" | "replaced",
  "relation": "SUPPLEMENT",
  "reason_code": "...", "applied": true,
  "routed_task_id": "task-...",
  "task": { /* RuntimeTaskResult.to_data() */ }
}
```

## 3. Kernel 输入路由

### 3.1 事件分派 `dispatch_input_event`

`kernel.py:3502`，按**事件类型**先分派，不做语义解释：

| 事件类型 | 处理 |
|---|---|
| `ApprovalResolutionInput` | `resolve_agent_approval`（审批答复） |
| `ClarificationReplyInput` | `resolve_agent_clarification`（追问答复） |
| `InterruptTaskInput` | `interrupt_agent_turn` |
| `CancelTaskInput` | 结算未开始批次 → `transition_task(CANCELLED)` |
| `SessionTextInput` | `resolve_session_input`（会话路由：建任务 / 直接答 / 追问） |
| `RuntimeTextInput` | `route_runtime_input`（对**已存在**任务做 steer/replace/status） |

### 3.2 活动任务输入路由 `route_runtime_input`

`kernel.py:3597`。核心是"**校验 + 原子入队**"，而不是立刻改状态：

1. 任务状态必须是活跃集（`EXECUTING` / `RUNNING_WORKFLOW` / `AWAITING_APPROVAL` / `AWAITING_USER` / `INTERRUPTED` / `CONFLICT`）。
2. 算 `request_hash = canonical_hash({text, explicit_intent, fallback_intent})`，用 `input_id` 查重：
   - 命中同 `input_id` 且 `request_hash` 相同 → **幂等重放**，直接返回既有 `RuntimeInputRoute`；
   - 命中但 `request_hash` 不同 → 报错 `input_id was reused with different input`。
3. 组 `RuntimeInputContext`（`core/runtime_input.py`）：

```python
RuntimeInputContext(task_state, current_goal="",
    awaiting_clarification=False, awaiting_approval=False,
    pending_approval_kind="", pending_approval_action="",
    pending_approval_target="", pending_approval_risk="")
```

4. 没有显式/兜底意图、也不在等审批/追问时，调**同一个**关系判断器（`kernel.py:3617` 起）把关系映射成控制意图：`SUPPLEMENT→STEER`、`REPLACE→REPLACE`、`STATUS_QUERY→STATUS_QUERY`，且 `confidence >= 0.85` 才采纳。
5. `RuntimeInputRouter().route(...)` 产出 `RuntimeInputRoute`：

```python
RuntimeInputRoute(intent, confidence, reason_code,
                  requires_confirmation, applied=False, router_version="deterministic-v1")
```

6. `applied = steering_kind is not None and not requires_confirmation`；若当前在等审批，需要从 `active_agent_checkpoint` 恢复检查点，否则 `applied=False`（reason `approval_has_no_resumable_agent_checkpoint`）。
7. 落库 `runtime_input.routed` 事件，payload = `route.to_event_data(text, input_id)` + `request_hash`。

### 3.3 steering 的排队与安全边界

- 排队的 durability 记录是 `steering.queued`（`kernel.py:3812`）：

```jsonc
{ "steering_id": "...", "inbound_sequence": 7, "kind": "STEER"|"REPLACE",
  "text": "...", "text_hash": "...", "request_hash": "..." }
```

- 落地在 `_apply_pending_steering`（`kernel.py:7283`），只允许三个**安全边界**（safe point）：
  `before-model`、`before-tool-batch`、`before-tool`。
- 落地事件 `steering.applied`（`kernel.py:7500`）：

```jsonc
{ "turn_id": "...", "steering_ids": [...], "inbound_sequences": [...],
  "safe_point": "before-model", "goal_revision": 3,
  "replaced_pending_tool_calls": 0,
  "committed_mutation_count": 2, "completed_tool_execution_count": 5,
  "checkpoint_hash": "...", "working_memory_revised": false,
  "task_spec_revision": 2, "task_spec_hash": "..." }
```

- `STEER` **不改**目标与契约（TaskSpec）；`REPLACE` 会重签契约（`task_spec.revised`，`writer="runtime-steering"`）；两者都**不回滚**已提交的事实（`committed_mutation_count` 只记录不回退）。
- steering 以 user 角色消息追加，边界标记 `boundary=user_runtime_steering`（JSON 信封）。

### 4.3 状态机与 `transition_task`

`TaskState`（`core/task.py:39`）：
`CREATED / INTAKE / RESOLVING_PROJECT / SELECTING_EXTENSIONS / ROUTING / PLANNING / RUNNING_WORKFLOW / EXECUTING / AWAITING_APPROVAL / AWAITING_USER / INTERRUPTING / INTERRUPTED / RESUMING / CONFLICT / VERIFYING / FINALIZING / SUCCEEDED / CANCELLED / FAILED`（终态 = `SUCCEEDED` / `CANCELLED` / `FAILED`，另加 `NEEDS_REVIEW` 作为"需人工裁决"的终态）。

对外收敛的 `Phase1TaskState`（`core/task.py:23`）：
`PREPARING / RUNNING / WAITING / INTERRUPTED / NEEDS_REVIEW / DONE / FAILED / CANCELLED`。

`transition_task`（`kernel.py:8930`）：
- 先用 `LEGAL_TRANSITIONS` 校验合法性；
- 必要时先补 `config.snapshot` 事件（payload：`revision / effective_config_hash / toolset_hash / adapter_lock_hash / policy_hash / provider_capabilities_hash`）；
- 写 `task.state_changed`：

```jsonc

  "reason": "SDK verifier started",
  "intent": "cancel", "schema_version": 1 }   // intent 仅显式操作时带
```

- 终态额外做：`_record_session_task_state`（会话侧 `session.task_state_updated`）、关闭取消作用域、CANCELLED 记入内存取消集。

## 5. 规划：把用户请求变成"契约"

### 5.1 `plan_task_spec`

`kernel.py:3289`。**幂等守卫**：`if planner is None or current.outcomes: return current`（已有 outcomes 就不再重规划）。

流程：
1. `_task_spec_planning_context(task)`（`kernel.py:3038`）取当前请求与规划上下文（含会话权威内容、非权威背景）。
2. `planner.propose_task_spec(current_request, planning_context)` → 原始 dict。
3. `TaskSpecProposal.from_data(raw, require_acceptance_criteria=True)` 校验。
4. `_demote_unresolvable_criteria`：无法解析的 `evidence_reference` **降级为 `rubric`**（不是硬失败），并写 `task_spec.criteria_demoted`。
5. `_demote_background_leaks`：把从非权威背景抄进验收条目的内容降级，写 `task_spec.background_leak_demoted`（INV-9：权威是数据边界，不靠提示词自觉）。
6. 剥离模型提交的**运行时判据**，由运行时重新派生（见 5.3）。
7. `TaskSpecSnapshot.from_proposal(...)` → 写 `task_spec.revised`。
8. 任何异常 → `task_spec.planning_failed`（`recoverable: true`）后抛出。

### 5.2 规划器（planner）的模型调用

`adapters/model_task_spec_planner/planner.py:44` `propose_task_spec`：
- **一次独立模型调用**（`ModelCallPurpose.TASK_SPEC`），system prompt 要求"把用户请求翻译成项目无关的 Task SPEC"；
- 支持工具时挂唯一工具 `planner.submit_task_spec`，schema = `TASK_SPEC_PROPOSAL_SCHEMA_V1`；
- 不支持工具时要求返回纯 JSON；
- `max_output_tokens=1200`，最多 **2 次尝试**（第二次带 `correction` 提示）；
- 两次都不合格 → `model did not submit one valid Task SPEC proposal`。

### 5.3 proposal 数据格式（`TASK_SPEC_PROPOSAL_SCHEMA_V1`，`core/task_spec.py:669`）

```jsonc
{
  "schema_version": 1,
  "goal": "…(1..2000 字)",
  "scope": ["."],                    // ≤50
  "constraints": [],                 // ≤50
  "acceptance_criteria": [           // 1..28（29/30 留给运行时判据）
    {
      "criterion_id": "ac-1",        // ≤120
      "description": "…",            // ≤1000
      "verification_kind": "workspace_integrity" | "post_mutation_command"
                          | "evidence_reference" | "rubric",
      "evidence_reference": null     // 仅 evidence_reference 允许，且必须 event:/tool_call:/mutation: 前缀
    }
  ],
  "outcomes": [                      // 1..30
    {
      "outcome_id": "outcome-1",
      "description": "…",
      "kind": "ANSWER" | "EVIDENCE" | "WORKSPACE_DELIVERY" | "COMMAND_RESULT"
             | "PROCESS_STATE" | "ARTIFACT_DELIVERY" | "USER_DECISION",
      "required_effects": ["observe"|"mutate"|"execute"|"interact"|"control"],
                         // schema 明确排除 unspecified 与 internal
      "required": true,
      "depends_on": ["outcome-0"],
      "completion_policy": "EXPLICIT_ACCEPTANCE" | "ATOMIC_ACTION",
                          // 枚举实际有三值，schema 排除 REQUIRED_EFFECTS（新工作不得使用）
      "atomic_action": { "tool_name": "...", "arguments": {} }
    }
  ],
  "continuation_policy": { "mode": "NONE" | "WHEN_USER_DECISION_REQUIRED"
                                 | "AFTER_COMPLETED_UNIT" }
}
```

**校验规则**（`TaskSpecProposal.__post_init__`、`TaskOutcomeProposal.__post_init__`）：
- 非会话类结果（非 `ANSWER`/`USER_DECISION`）**必须**至少声明一个 effect；
- effect 不能是 `unspecified` / `internal`，不能重复；
- `depends_on` 不能指向自己，必须唯一；
- `ATOMIC_ACTION` 必须有 `atomic_action.{tool_name, arguments}`；非 `ATOMIC_ACTION` 不允许带。

### 5.4 契约快照（`TaskSpecSnapshot`，`core/task_spec.py:777`）

```python
task_id, revision, goal, scope, constraints,
acceptance_criteria: tuple[TaskAcceptanceCriterion, ...],
outcomes: tuple[TaskOutcomeSnapshot, ...],
continuation_mode: TaskContinuationMode, schema_version: int, content_hash: str
```

`TaskAcceptanceCriterion`（`core/task_spec.py:732`）：

```python
criterion_id: str, description: str,
verification_kind: TaskCriterionKind, evidence_reference: str | None
```

`TaskCriterionKind`（`core/task_spec.py:43`）：

| 值 | 谁写的 | 判定方式 |
|---|---|---|
| `workspace_integrity` | 模型 | 磁盘哈希 vs 改动流水 |
| `post_mutation_command` | 模型 | 改动后跑命令并成功 |
| `evidence_reference` | 模型 | 引用已有 `event:`/`tool_call:`/`mutation:` |

| `post_mutation_command` 判据 | `TASK_SPEC_POST_MUTATION_COMMAND` | 是（有改动但命令未通过） |
| `evidence_reference` 判据 | `TASK_SPEC_EVIDENCE` | **否**（证据是既成事实，不是待办） |
| 未闭合 Evidence Question | `EVIDENCE_QUESTION` | 是 |
| 后置命令验证 | `POST_MUTATION_VERIFICATION` | 是 |
| 未解决的 effect 失败 | `UNRESOLVED_EFFECT_FAILURE` | 是 |
| 无裁判的评判判据 | `JUDGED_CRITERION_WITHOUT_JUDGE` | 是 |
| 工具恢复 | `TOOL_RECOVERY_REQUIRED` | 是（不在本函数产生，见下注） |
| `rubric` / `goal_alignment` | — | **不产 gap**（留到最终验收） |

> `TOOL_RECOVERY_REQUIRED` 由回合内的恢复批次路径产出（`kernel.py:13244`），随后传给 `_suspend_incomplete_recoverable`，不属于 `_completion_readiness_gaps`。

### 9.2 评估 `_evaluate_completion_readiness`

`kernel.py:8164`。组装 probe：

```python
CompletionReadinessProbe(
    goal, gaps, remaining_model_calls, remaining_tool_calls,
    available_read_tools, forced_wrap_up=False, evidence_item_count,
    successful_tool_calls, available_effects: frozenset[ToolEffect],
    available_tools, unresolved_failures)
```

调 `policy.evaluate(probe, state)` → `CompletionReadinessDecision(action, reason, state, gaps)`。

四态（`CompletionReadinessAction`）：

| action | 含义 |
|---|---|
| `COMPLETE` | 没有 required 缺口，可以收尾 |
| `CONTINUE` | 还差可补的活，继续循环 |
| `REPORT_INCOMPLETE_RECOVERABLE` | 还能补但本轮容量用尽 → 挂起等用户继续 |
| `REPORT_BLOCKED` | 补不了或纠正次数到顶 → 如实报告 |

策略判定（`adapters/rule_based_completion_readiness/policy.py:56`）：required 为空→`COMPLETE`；反复同样的缺口→`REPORT_BLOCKED`（reason `required_gaps_unchanged_across_continuations`）；缺口 effect 都在可用集合内且还有额度→`CONTINUE`。

写 `completion.readiness_evaluated`：

```jsonc
{ "turn_id": "...", "action": "CONTINUE", "raw_action": "CONTINUE",
  "reason": "required_capability_is_available",
  "mode": "LEGACY_GATE", "enforced": true, "forced_wrap_up": false,
  "remaining_model_calls": 5, "remaining_tool_calls": 20,
  "available_effects": ["execute","mutate","observe"],
  "gap_count": 1,
  "gaps": [ { "gap_id": "...", "kind": "REQUIRED_DELIVERY_UNSATISFIED",
              "required_effects": ["mutate"], "candidate_tools": ["core.apply_patch"],
              "required": true, "recoverable": true, ... } ],
  "state": { "continue_attempts": 1, "disclosure_attempts": 0,
             "stalled_continuations": 0, "last_action": "CONTINUE" } }
```

策略崩了 → `completion.readiness_failed`（`fail_closed: true`）并抛出（INV-5：判定器坏了绝不接受"完成"）。

## 10. 最终验收

`verify_task_acceptance`（`kernel.py:9186`）：

1. 取任务快照，状态必须是 `VERIFYING`（或 `EXECUTING` 且非 LEGACY 的观测态）；
2. `TaskSpecProjector.project(task_id, goal, events)` **从事件重放**出契约（不是读快照字段）；
3. 若存在 `turn.completed` → 强制校验答复完整性 `_verify_answer_completeness`；
4. 算工作区证据：逐条 `MutationRecord` 比"磁盘当前哈希 vs `after_hash`"；
5. 按契约逐条判定：

| 判据 | 判定 |
|---|---|
| `workspace_integrity` | 全部哈希一致→PASSED，否则 FAILED；零改动时天然 PASSED |
| `post_mutation_command` | 零改动→`NOT_APPLICABLE`；有改动但无成功命令→BLOCKED；命令失败→FAILED |
| `required_effect` | 契约声明的 mutate/execute 都有耐用记录→PASSED，否则 FAILED（逐 effect 出证据） |
| `rubric` / `goal_alignment` | 有界裁判模型；无裁判→BLOCKED（INV-10：没人能判的条目不静默通过） |
| `evidence_reference` | 解析引用；解析不到→BLOCKED |

6. 汇总：任一 FAILED→整体 FAILED；否则任一 BLOCKED→整体 BLOCKED；否则 PASSED；
7. 评估证据等级（`evidence_level`），写 `verify.criterion_completed`（每条）+ `verify.completed`（整体）。

数据格式：

```python
TaskVerificationResult(task_id, status: AcceptanceStatus,
                       criteria: tuple[AcceptanceResult, ...],
                       evidence_level: EvidenceLevelAssessment | None)

AcceptanceResult(criterion_id, status, evidence: tuple[Evidence, ...])

Evidence(kind, assertion, observed, source_step_id, passed, artifact_path=None)

AcceptanceStatus: passed | failed | blocked | not_applicable
```

`verify.criterion_completed` payload：

```jsonc
{ "criterion_id": "required-effect-delivery", "status": "failed",
  "evidence": [ { "kind": "tool_effect",
                  "assertion": "the contract requires a performed mutate action",
                  "observed": "no durable record exists",
                  "source_step_id": "verifier", "passed": false,
                  "artifact_path": null } ] }
```

`verify.completed` payload：`{ "status": "failed", "criterion_count": 8 }`。

## 15. 一处必须记住的语义边界

**"模型说了什么"和"运行时认定发生了什么"是两条独立的线**：

- `llm.completed` = 模型产出了一段内容（可能只是临时总结，也可能最终没被采纳）；
- `session.task_result_recorded` = 这段内容**确实交给了用户**；
- `verify.completed` = 交付是否达标；
- `task.state_changed → SUCCEEDED` = 任务正式完成。

四者顺序固定、缺一不可，重启后也只以持久事件为准（`_persisted_assistant_text` 只认第 2 条）。
