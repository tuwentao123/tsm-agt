# P2 完成审查的只读闭环

本次变更新增 `CompletionAudit` 输入、结论与 SQLite 审计账本，并在 SDK 完成路径上将确定性验收结果交给审计器判定。独立的 `compose_completion_audit_application` 正确限制为 Runtime/Profile reader 和只读工具，账本也单独落在 `completion_audit.db`。但生产完成路径没有调用这个 composition，也没有执行审计器提出的补证读取；它仅重新提交原始快照。更严重的是，确定性验收为 `BLOCKED` 时仍可被审计器判为 `PASS`，SDK 会将任务标为 `SUCCEEDED`。Watch for: **confirmed** — 未通过的确定性验收可被升级为成功；**confirmed** — `NEEDS_EVIDENCE` 不会读取要求的 source ref，隔离补证闭环未实现；**confirmed** — 专用只读审查 composition 未接入完成路径，无法兑现审查运行时隔离。

**Verdict**: NEEDS_CHANGES

## High-level view

完成状态机在确定性 `FAILED` 时直接失败，这是正确的优先级；但其余状态没有被限制为必须 `PASSED`。审计器只排除字符串 `FAILED`，因此 `BLOCKED` 会在存在形式合法的事件引用和 workspace fingerprint 时走到 `PASS`，绕开了未满足的验收债务。

`NEEDS_EVIDENCE` 的数据模型可表达 `requested_read_refs`，特别是画像候选与否定回答冲突时会返回 source ref；SDK 却只重跑一次 `run_completion_audit`。第二次构造的是同一 Worker 答案、同一验收和同一运行时引用集合，没有通过只读工具读取这些 ref，故补证结果不可变化。

只读 composition 的注册集合本身隔离了 process、mutation、approval、working memory 和 profile maintenance，但它只被独立测试直接构造。主应用的 Kernel 在原应用进程中直接调用注入的 audit port，既不启动专用 reader runtime，也不把一个受限的审查 turn 作为执行单元；审查策略目前只能基于预组装元数据作判断。

## `BLOCKED` 验收在审计层丢失了阻断语义

`TaskVerificationResult.passed` 只会在状态为 `PASSED` 时返回真；`BLOCKED` 代表仍有未完成的验收债务。SDK 只对 `FAILED` 直接转 `FAILED`，随后将 `BLOCKED` 交给 `RuleBasedCompletionAuditor`。该策略同样只检查字符串 `"FAILED"`：有任意 `event:`、`tool_call:` 或 `mutation:` 前缀的引用及非空 fingerprint 后，即返回 `PASS`。SDK 将这个 `PASS` 直接转为 `FINALIZING → SUCCEEDED`。

已用最小输入验证该行为：`{"status": "BLOCKED", "passed": false}`、`("event:1",)` 和非空 fingerprint 返回 `PASS`。这不是证据不足时进入 `NEEDS_REVIEW` 的保守失败，而是实际将不满足的确定性验收提升为成功。审计应只能为确定性 `PASSED` 提供第二道可信度门槛；`BLOCKED` 应保留在 `NEEDS_REVIEW`（或仅在真实补证后重新运行确定性验收），不能被审计结论覆盖。

## `NEEDS_EVIDENCE` 没有形成一次受限的只读补证

策略在回答包含“没有”“不存在”等否定词且 profile sections 有 source refs 时会返回 `NEEDS_EVIDENCE` 和至多八个 `requested_read_refs`。SDK 的循环只重复调用 `kernel.run_completion_audit`；它没有读取 `requested_read_refs`，也没有将 read result、更新后的 source hash 或新的可信 evidence ref 写进下一份输入。`run_completion_audit` 收集的 event 类型还固定为 `llm.completed`、`turn.completed`、`verify.completed`，审计完成事件本身也不会改变候选证据。

因此这条分支无论首次因缺少引用还是因画像冲突返回 `NEEDS_EVIDENCE`，第二次在相同条件下仍会得到同一结论，最后进入 `NEEDS_REVIEW`。一次的数量上限已存在，但“补证”没有实际动作。应由隔离 reader runtime 只读取审计记录要求的 ref，限制读取次数为 `MAX_AUDIT_READ_TOOL_CALLS`，将可回放的读取引用带入后续审计；若仍无法确定才转 `NEEDS_REVIEW`。

## 只读 composition 停留在测试入口，未成为审查执行边界

`compose_completion_audit_application` 注册 `SQLiteRuntimeReader`、`SQLiteProjectProfileReader`、`CoreReadOnlyToolProvider` 和 `CodeIntelligenceToolProvider`，未注册 process、mutation、interaction、memory、working memory 或 profile maintenance provider。这个边界符合只读审查 composition 的设计目标。但 SDK 的完整路径持有原 `application.kernel` 并调用其 `run_completion_audit`，后者直接读取主应用的 RuntimeStore 与 profile store 后调用同一进程中的 policy；项目内没有任何生产调用点使用 `compose_completion_audit_application`。

因而目前不可能在审计期间执行受限工具读取，也没有独立审查 turn 的预算、上下文和 capability 集合。虽然传给 policy 的 `CompletionAuditInput` 没有 Worker checkpoint 或 raw tool body，数据载荷隔离不等于运行时能力隔离；后续把审计器替换为模型或工具驱动实现时，会直接失去这一安全边界。将 composition 作为 SDK 完成阶段的真实执行单元，或抽取一个等价、显式受限的 audit runtime factory，才能保证审查不继承 Worker 的 memory、权限和工具结果。

## 覆盖范围

`tests/test_completion_audit.py` 覆盖了有 `event:3` 的 PASS、画像冲突返回 source ref、以及单独构建 composition 的只读工具集合与账本持久化；定向命令 `tests.test_completion_audit tests.test_cli_standalone_finalization tests.test_project_profile` 运行 9 项均通过。未覆盖 `BLOCKED` 验收不得成功、`NEEDS_EVIDENCE` 必须实际读取 `requested_read_refs` 且只读一次、以及 SDK 从生产 composition 进入隔离审查运行时；这三项缺口使当前绿测无法验证 P2 的关键闭环。
