# 完成审查与画像状态仍有四处可信闭环缺口

本轮复核后仍有四个可复现缺陷：完成审查可在源码覆盖不完整时接受否定结论，stale job 可重复推进画像 revision，P3 事件投影可永久误报 pending/dirty。Watch for: **confirmed** — 8k 源码前缀被当作完整 source；**confirmed** — 读取前 8 个冲突 ref 后，第 9 个未读 ref 不再阻止 PASS；**confirmed** — stale replacement 与 mutation job 并存时重复构建 revision；**confirmed** — 历史 refresh 事件使嵌套投影永久 DIRTY。

**Verdict**: NEEDS_CHANGES

## High-level view

**confirmed。** 补证源码固定截取文件前 8000 字符且没有完整性元数据；模型返回 PASS 时，解析器只检查是否存在任意 `audit_source_evidence`，文件后部事实可以被遗漏。

**confirmed。** 否定结论虽已纳入全部 profile sections，但一次补证只请求前 8 个 ref；存在任意 source evidence 后，剩余未读候选不再阻止 PASS。

**confirmed。** 失效 target job 的 replacement 与无 target 的 workspace-mutation job 可同时存在；两者按同一最新 workspace 构建后都会无条件推进 revision。

**confirmed。** P3 实时顶层状态查询 profile store，但 `TaskRuntimeProjector` 把任意历史 `project_profile.refresh_requested` 当作当前 pending，结果对象可同时携带互相矛盾的画像状态。

## 8k 文件前缀不足以证明否定结论

**高严重度，confirmed。** `collect_completion_audit_evidence()` 校验整文件 hash 后，只把解码结果的前 8000 字符放入 `AuditSourceEvidence`；数据结构和事件都没有 `truncated`、总字符数或覆盖范围。`_parse_model_verdict()` 在 `audit_source_evidence` 非空时允许否定结论 PASS，并不要求 excerpt 覆盖 profile 候选对应的符号或位置。

最小复现使用 9000 字符填充、文件尾部包含 `def api()` 的源码：审查输入 excerpt 长度为 8000，不含 `def api`，审查模型返回 PASS 时解析器仍接受 PASS。文件 hash 只能证明文件未变；应提供目标符号附近的结构化 observation，或携带明确 coverage 并在不完整时禁止否定结论 PASS。

来源：`src/tsm_agt/core/kernel.py:9921-9932`，`src/tsm_agt/core/completion_audit.py:23-35`，`src/tsm_agt/adapters/completion_audit.py:252-263`。

## 第九个冲突 source ref 可在未读时被忽略

**高严重度，confirmed。** `_unread_conflicting_profile_refs()` 只返回前 8 个。一次补证后，解析器以“存在任意 `audit_source_evidence`”作为已补证条件，不再检查剩余未读 ref，因此超过上限的候选不会强制 `NEEDS_EVIDENCE` 或 `UNDECIDABLE`。

最小复现构造 9 个冲突 section，只为前 8 个提供 source evidence；审查模型返回 PASS 后，最终 verdict 为 PASS，`requested_read_refs` 为空，第 9 个 ref 保持未读。单次最多读取 8 个是预算约束，超预算时应 fail closed。

来源：`src/tsm_agt/core/kernel.py:9953-9974`，`src/tsm_agt/adapters/completion_audit.py:252-263,297-309`，`src/tsm_agt/sdk/runtime.py:1304-1321`。

## stale replacement 与 mutation job 会重复推进画像 revision

**中严重度，confirmed。** worker supersede 旧 target job 后会 enqueue 当前 fingerprint 的 replacement；已有 workspace-mutation job 使用空 target，去重键不同，因此可以与 replacement 同时排队。`complete_job()` 对两次构建都无条件执行 `current.revision + 1`，没有检查 current profile 已具有相同 fingerprint/input hash。

最小复现从 r1 同时排入旧 `TASK_SETTLED` job 和 mutation job：旧 job 被 supersede，mutation job 生成 r2，replacement 随后对相同 workspace 再生成 r3。应在 replacement 入队或 complete 时与当前 profile/待处理 mutation job 原子去重。

来源：`src/tsm_agt/adapters/local_profile_scheduler.py:86-116`，`src/tsm_agt/adapters/sqlite/project_profile.py:105-139,175-184`。

## P3 事件投影永久保留 pending/dirty

**中严重度，confirmed。** `TaskRuntimeProjector._project_profile_data()` 只要历史事件中出现过 `project_profile.refresh_requested`，就永久设置 `pending_refresh=true` 并覆盖 freshness 为 `DIRTY`；没有完成、supersede 或当前 store 状态来清除它。SDK 顶层 `project_profile` 通过 `has_pending_refresh()` 得到实时值，因此同一个 `RuntimeTaskResult` 可能暴露互相矛盾的两套状态。

Web 优先使用顶层状态，并已显示 audit source 与 fingerprint stop reason；但项目画像文案只消费 `freshness` 和 `revision`，`pending_refresh` 与 `section_count` 未显示。应让统一投影读取当前 profile/job 事实，或投递可配对的 refresh 完成事件，并让 Web 显示规范字段。

来源：`src/tsm_agt/core/task_runtime_projection.py:187-217`，`src/tsm_agt/core/kernel.py:6740-6767`，`src/tsm_agt/sdk/runtime.py:865-895`，`src/tsm_agt/web/app.py:1579-1605`。

## 验证范围

定向执行 7 个相关测试文件，结果为 29 passed。另执行三个最小复现：长文件尾部实现仍被否定结论 PASS；9 个冲突 ref 仅读 8 个后仍 PASS；stale replacement 与 mutation job 将同一次变更从 r1 推进到 r3。现有绿测未覆盖这三个场景，也未覆盖刷新完成后嵌套投影清除 pending/dirty。
