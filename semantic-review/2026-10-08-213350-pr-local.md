# 通用证据合同迁移

迁移已将 `TaskContract`、`EvidenceFact` 和 completion gap 接入任务创建与工具执行账本：SDK 与 `POST /tasks` 可在创建时提交合同，`task.created` 保存合同，成功且已提交的工具结果保存 facts。**[confirmed]** 运行时仍固定调用一个函数，合同中的 `gates` 不参与决策，合同只可创建时写入且不投影给模型或 API 管理面。`BLOCKED` 在 single-loop/SDK 中会返回 `AgentTurnIncomplete` 并保持 Task 为 `EXECUTING`，而不是主动标记 `FAILED`；但没有真实用户合同阻塞路径的端到端验证。**[confirmed]** 工具协议纠正既漏掉 provider/响应校验抛出的可恢复错误，也会把没有 ToolResult 的被拒绝 ToolCall 留给下一轮请求。

Watch for: **[confirmed]** `EvidenceGatePort` 和合同内 `gates` 都没有接入运行时；**[confirmed]** provider 或模型响应校验的 `RecoverableToolProtocolError` 会逃出 single-loop；**[confirmed]** 已拒绝批次的 assistant ToolCall 会留在下一次请求历史里却没有对应 ToolResult。

**Verdict**: NEEDS_CHANGES

## High-level view

**[confirmed]** 合同不是独立可管理对象：`TaskContract` 仅在创建时写入，没有读/改/接受草案入口，也不进入初始模型请求。这使严格合同只能在模型尝试结束后才反馈。

**[confirmed]** Evidence Gate 不是可替换 policy。`EvidenceGatePort` 未被 composition 注册或注入，completion 直接调用 `evaluate_evidence_contract`；合同中的 `EvidenceGate` 列表也没有消费者。

`BLOCKED` 会写入 `turn.incomplete_boundary`，SDK 投影为 `incomplete`，没有进入失败路径。**[likely]** Task 仍为 `EXECUTING`，没有稳定的 blocked/awaiting-user 状态或恢复 action，调用方必须从诊断事件判断停顿原因。

**[confirmed]** legacy phase 把模型调用、响应校验和批次校验放进同一个 recoverable-protocol 分支；single-loop 只恢复批次 schema/未知工具错误。局部 correction 还会保留无结果的 ToolCall，而 single-loop 没有调用既有的 ToolCall/ToolResult 邻接校验。

## 固定 evaluator 使 EvidenceGate 不能替换

`ports/evidence.py` 定义了 `EvidenceGatePort.evaluate(contract, facts, capabilities)`，但它没有被注册到 `AdapterRegistry`、没有进入 `KernelDependencies`，也不在 `composition.py` 的唯一性校验中。`core/single_loop/contracts.py` 直接 import 并调用 `evaluate_evidence_contract`。**[confirmed]** 自定义 Gate 没有可到达的注入点，替换实现只能改 `contracts.py` 或 loop 的调用链。

合同里的 `gates: tuple[EvidenceGate, ...]` 也没有被 evaluator 使用：它只遍历 `contract.evidence_requirements`，以 `requirement.kind` 与工具的 `evidence_capability_ids` 匹配，`gate_id` 和 `requirement_ids` 不影响 PASS、CONTINUE 或 BLOCKED。**[confirmed]** API 可持久化该字段，却不会改变任何决策。

## 合同只是在 task.created 里的不可见快照

SDK `create_task` / `submit_task` 和 Web `POST /tasks` 接收 `TaskContract`/`evidence_contract`，`Kernel.create_task` 将 `to_data()` 写入 `task.created`，所以“创建并持久化”在这一条窄路径上成立。**[confirmed]** 全仓库没有 contract 读取、修改、接受 draft、暂停或恢复接口；任务结果和 Web projection 也不返回该 payload，Spec 所需的用户/API 可查看、修改、采用模型草案的独立 Goal/Contract service 不存在。

同一个 `command_id` 重放时只比较 goal 与 workspace，忽略 `evidence_contract`。第一次无合同、第二次用相同 command id 提交 USER 合同（或反过来）会返回旧 Task，既不冲突也不更新事件。**[confirmed]** 客户端会以为严格合同已采用，而 durable 账本仍使用旧合同。

`evidence_contract` 在创建与 final-completion validation 之间不投影到 model request。`guidance` 和 `objective` 不在模型首轮可见，只有模型给出最终文本后，loop 才以 completion continuation 反馈 requirement。**[confirmed]** 这偏离自由文本合同“引导模型和 judge”的目的，并消耗一次无约束的模型调用。

## BLOCKED 会成为 incomplete，但没有稳定的 blocked 生命周期

当 evaluator 返回 BLOCKED，`_can_recover_completion` 返回 false，`_incomplete_boundary` 写入 `turn.incomplete_boundary` 并返回 `AgentTurnIncomplete`。SDK 的 `_finish_agent_result` 投影 `status="incomplete"`，保持 Task 为 `EXECUTING`，不调用 `complete_task`，也不走 `FAILED`。**[confirmed]** 指定的“不将能力缺失伪装成模型失败”在 single-loop SDK 路径成立。

**[likely]** 这不是稳定 blocked 状态：没有 `task.state_changed`、`AWAITING_USER` 信息或专门恢复/安装 capability 的 action，只有诊断事件。测试分别验证 evaluator 的 BLOCKED 决策和另一种 mutation gap 的 SDK incomplete 投影，却没有从 USER `source.artifact` 合同、无 satisfier capability 的真实 Agent turn 断言不失败、持久可读和恢复行为。

## protocol correction 没有覆盖所有正确的错误来源

single-loop 只在 `_validate_tool_batch_proposal` 外捕获 `RecoverableToolProtocolError`，所以未知工具和参数 schema 错误会生成 `tool.protocol_rejected`。**[confirmed]** `_complete_agent_model_request` 和 `_validate_agent_response` 均发生在该 try 块之前；provider 文本/流式工具协议错误，以及 `tool_call_emitted_while_disabled` / `invalid_text_tool_protocol` 会直接逃出 loop。legacy `turn_phases.py` 统一捕获这三类来源，single-loop 行为不一致。

局部 catch 触发时，loop 已将含被拒绝 ToolCall 的 `response.message` 写入 `state.messages`，随后只添加 USER correction；call 未执行，因此没有 ToolResult。**[confirmed]** single-loop 的 `_prepare_model_call` 不调用 `Kernel._normalize_and_validate_model_boundary`，该边界校验只在 legacy turn phase 使用。下一次请求会携带孤立的 assistant ToolCall，依赖 provider 对不符合 ToolCall/ToolResult 邻接约束历史的处理。

## Typed facts 的完整性没有在公共边界强制

`ToolResult` 禁止失败结果携带 facts，却不禁止 `truncated=True` 的成功结果携带 `EvidenceFact(complete=True)`；`_evidence_facts` 也只检查 committed 和 `result.ok`，不会剔除截断结果。**[confirmed]** 当前 GitHub 和网络 normalizer 虽避免为已识别的截断读取生成 complete fact，通用 contract 仍允许任意 provider 直接满足 `minimum_count` 或 predicates，违反“失败、截断、未知结果不得产生 complete evidence”的约束。

## 覆盖范围未覆盖公共合同与恢复行为

`test_single_loop_completion_contracts.py` 覆盖纯函数级 USER/DRAFT、exact capability 和 distinct facts；`test_sdk_runtime.py` 覆盖没有严格合同的 mutation gap 不转 FAILED。**[confirmed]** 缺少 Web `POST /tasks` 合同入参的端到端测试、SDK durable 合同恢复、command-id 合同冲突、可插拔 Gate、真实 BLOCKED 生命周期，以及两类 `RecoverableToolProtocolError` 的 single-loop 回归测试。测试命令未能运行：环境没有 `python`，`python3 -m pytest` 也缺少 `pytest` 模块。
