# 结构化运行时输入的确定性分流

本次改动引入 `RuntimeInputEvent` 联合类型，并让 SDK 与交互式 CLI 的审批、澄清回复和部分中断路径进入 `Kernel.dispatch_input_event`。其中审批和澄清事件会直接调用各自的 pending-request 解析协议，不会落入 `RuntimeInputRouter` 的普通文本路径；这一点符合 `FLOW_AND_STATE_MACHINE_REDESIGN_SPEC.md` 第 11 节第 1 步的核心目标。`RuntimeInputRouter` 也已将等待澄清时的普通文本固定为 `AMBIGUOUS`，不再把“选第二个”猜成澄清答案。改动仍在取消时留下已挂起的协议记录，并新增了会在第二次提交后失效的 Web UI。Watch for: **confirmed** 取消后的旧审批或澄清请求仍会被存储层当作 pending 查到；**confirmed** Web UI 所有任务复用同一个幂等键。  
**Verdict**: NEEDS_CHANGES

## High-level view

`dispatch_input_event` 将 `ApprovalResolutionInput` 和 `ClarificationReplyInput` 直接交给已有的、带 request/token 校验的处理逻辑，因此结构化澄清回复不会被文本路由或分类器重新解释。普通文本仍经 `RuntimeTextInput` 才能进入 `route_runtime_input`，与规格要求的协议层先分流一致。

取消事件目前只触发通用状态迁移。通用迁移会保留 `pending_approval` 和 `pending_clarification`，而存储层按 pending ID 查找时不筛选 Task 状态；已取消任务因此仍占有并暴露一个本应失效的结构化请求。

新增 Web UI 直接持有 `LocalEventApiServer` 的私有 client，并以固定的 `web-ui` 作为每次创建任务的 command ID。Kernel 将 command ID 作为创建任务幂等键，故页面只能可靠地创建第一个任务。页面还把 SSE 原文拼进 `innerHTML`，让任务进度中的字符串进入可执行的 HTML 上下文。

CLI 的交互式等待分支已改接 dispatcher，但 `approve`、`answer` 子命令及实时 `/interrupt` 等入口仍直调旧 Kernel 方法。当前它们恰好调用同一确定性实现而没有重识别，但输入协议的单一入口没有真正建立，后续改动容易产生行为分叉；相应的事件级回归覆盖也缺失。

## 取消后的 pending 请求仍可被寻址

`Kernel.dispatch_input_event` 对 `CancelTaskInput` 的处理仅调用 `transition_task(..., CANCELLED, ...)`。`TaskSnapshot.transition()` 对任何状态迁移都复制 `pending_approval` 和 `pending_clarification`；终态只清除 agent/onboarding checkpoint。SQLite 的 `find_task_by_pending_approval` 与 `find_task_by_pending_clarification` 遍历全部 `runtime_tasks`，只按请求 ID 匹配，不限制为 `AWAITING_APPROVAL` 或 `AWAITING_USER`。

因此，在审批或澄清等待期间取消任务后，SDK 或 CLI 接到旧 request ID 仍会定位该 `CANCELLED` Task，再在更深的恢复校验中失败。这个行为既让终态快照显示不存在的 pending 请求，也让过期交互继续占据 request ID。应在取消分支构造清除 pending 字段的终态快照，并写入审批/澄清取消事件；存储查询还应把当前等待状态作为防御性条件。**confirmed**：`src/tsm_agt/core/kernel.py:2510`、`src/tsm_agt/core/task.py:258`、`src/tsm_agt/adapters/sqlite/runtime_store.py:509`。

## Web UI 的幂等边界与内容边界

`POST /tasks` 固定传入 `command_id="web-ui"`。`Kernel.create_task` 已明确规定重用同一 command ID 时，目标、会话和工作区必须与第一次完全相同；不同目标会抛出 `ValueError`。即使目标相同，页面也只会重放第一个 Task，而不是创建用户再次点击 Run 所期待的新任务。**confirmed**：`src/tsm_agt/web/app.py:95`、`src/tsm_agt/core/kernel.py:3582`。

同一页面的 `EventSource.onmessage` 将整个 SSE payload 插入模板字符串后赋给 `timeline.innerHTML`。SSE 事件包含 runtime progress，页面没有任何 HTML 编码或可信类型边界；带有标签或事件属性的字符串会由浏览器作为 DOM 解析。应以 `document.createElement` 创建 card，并把展示内容赋给 `textContent`。**confirmed**：`src/tsm_agt/web/app.py:57`。

## dispatcher 只覆盖部分 CLI 入口

`_resolve_agent_approval`、`_resolve_agent_clarification` 仍直接调用 `resolve_agent_*`，实时 `/interrupt` 和退出处理也仍直接调用 `interrupt_agent_turn`。CLI 对同一协议存在两套接入边界，dispatcher 的事件契约无法成为唯一可审计的入口。

新增测试仅把一个现有澄清成功用例替换为 dispatcher 调用，并把 Router 对等待澄清的普通文本预期改为 `AMBIGUOUS`。未见审批事件、中断事件、取消事件、取消 pending 后旧 reply、SDK 路径或 CLI 独立子命令的覆盖。尤其第一项缺陷没有测试会暴露。**confirmed**：`src/tsm_agt/cli.py:1620`、`src/tsm_agt/cli.py:2141`、`src/tsm_agt/cli.py:1744`、`tests/test_clarification.py:118`、`tests/test_runtime_input_router.py:61`。
