## 状态边界

- 最新成功写入覆盖“需要恢复”的判断；此前失败仍可审计，但不会继续触发过期的失败提醒。
- 同一 Task 跨 turn 恢复时，保留清单与 revision；本轮维护次数从当前 turn 的执行账本计算。
- 3200 UTF-8 bytes 上限保留。有效事项 ID 最长 120 字符，完整保留；无可靠完整 ID 的行省略并标记需要读取完整清单。
- 在预算压力下先删低优先级条目和动作详情，再缩短说明或验收文本；不截取事项 ID 生成可写入的假 ID。
- 用户只要求分析、暂停或将部分工作留待后续时，未完成事项可以继续保留，不能据此恢复旧实施或虚报完成/阻塞。

两组均使用配置中的 `OpenAI-GPT-5.1`、high 推理强度和同一评测器，CompletionReview 关闭。

### 评测判定的限制

原始 `*-summary.json` 的 `behavior_pass` 是粗粒度检查，不能代表以上逐项抽查全部通过：

- 小改动基线用了 `foo  bar` 等正确示例，但静态标记只查 `a b`，造成该例机械判定失败；不能据此宣称优化后才会维护小改动。
- 落后状态例没有修改代码，机械判定没有要求新一次检查通过；两组都在检查终态未知时勾选，其通过标记不能证明完成条件满足。
- 范围改变例只检查了没有越界修改和虚报完成，未检查暂缓被误记为阻塞，也未检查旧事项是否仍被错误激活。
- `updates_before_final_tool_round` 只统计位置，不证明每次开始、切换都及时维护；新建自定义 ID 的事项与修改文件也不总能自动对应。
- 评测器独立跑通 unittest 只证明最终文件通过这些测试，不是模型已经执行验证的证据。命令在预检失败时可能没有进入执行账本，`checks=[]` 也不等于模型从未尝试过命令。

因此，本次能够确认的是维护规则、上下文及提醒已接通，真实模型在小改动及重试后的跨轮场景中出现了预期维护行为。
不能确认它已经稳定做到逐项及时更新，也不能宣称消除了提前结束、验证失败后放弃或错误勾选。
上述未通过场景完整保留，后续调整可以沿用同一组对照；本轮不增加强制结束拦截，也不为了清空清单自动勾选。
